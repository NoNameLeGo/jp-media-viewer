# Release Workflow

本文档记录从代码修改到发布新版本 APK 的完整操作流程，供后续 Agent 参考。

## 流程概览

```
PR merge → 更新版本号 → 更新 release notes → commit → tag → push → CI 自动构建并发布
```

## 详细步骤

### 1. 确认需要发布

以下情况需要发布新版本：
- 有 feature 或 bugfix commit 合并到 `main` 且尚未打 tag
- 用户明确要求 release

确定下一个版本号：
- 查看 `android/app/build.gradle.kts` 中的 `versionName`
- 小版本递进：betaX.Y.Z → betaX.Y.(Z+1)，versionCode +1
- 示例：beta0.5.3 → beta0.5.4，versionCode 29 → 30

### 2. 更新版本号

两个文件需要同步修改：

**`android/app/build.gradle.kts`**
```kotlin
versionCode = 30          // +1
versionName = "beta0.5.4" // 下一个版本号
```

**`AGENTS.md`**
```markdown
**Current version:** beta0.5.4 (versionCode 30)
```

### 3. 更新 Release Notes

**`release-notes.md`** 文件路径：`.github/release-notes.md`

将其从占位符模板修改为本次发布的真实内容，包括：
- 版本号声明（第一行）
- 新增功能（如有）
- 修复内容
- 始终保留版本信息和安装注意事项

示例：
```markdown
APK 自动构建版本 beta0.5.4。本次发布修复子文件夹模式下媒体排序混乱的问题。

### 修复内容
- 子文件夹浏览：启用子文件夹模式后，媒体改为按文件名排序

### 版本信息
- Release APK 继续使用稳定签名，支持从 beta0.0.8 及之后 release 签名版本覆盖安装
```

> 重要：每次发版前必须更新此文件，否则 Release 页面显示的将是旧内容。

### 4. Commit 并打 Tag

```bash
# 暂存所有修改
git add -A

# Commit，message 格式：release: betaX.Y.Z
git commit -m "release: beta0.5.4

- <change 1>
- <change 2>
...

Generated by AI"

# 打 tag，名称与 versionName 一致
git tag beta0.5.4
```

### 5. Push 触发 CI

```bash
# 先 push commit
git push origin main

# 再 push tag（触发 Release workflow）
git push origin beta0.5.4
```

### 6. 确认 CI 已启动

Push 后 GitHub Actions 会自动启动两个 workflow：
1. **push to main** — 构建 debug APK（仅验证）
2. **push tag（beta\*）** — 构建 signed release APK + 创建 GitHub Release

只需要确认对应 tag 的 workflow 已经开始，不需要守着等待构建完成。若构建或发布失败，用户会另行要求排查。

查看最近构建状态：
```bash
gh run list --workflow "Build APK" --branch beta0.5.4 --limit 5
```

确认输出中出现对应版本 tag（例如 `beta0.5.4`）且状态为 `queued`、`in_progress` 或 `completed` 即可。

### 7. Release 结果检查（仅在需要排障时）

默认不等待、不验证 Release 结果。只有用户要求确认发布结果或构建失败时，再访问 GitHub Releases 页面：
```
https://github.com/NoNameLeGo/jp-media-viewer/releases
```

排障时确认：
- 新版本 tag 已出现
- Release 正文显示正确的版本号和 changelog
- Assets 中包含对应版本号的 release APK（如 `jp-media-viewer-beta0.5.4-release.apk`）

## 注意事项

- **不要本地运行 Gradle 构建** — 用 GitHub Actions 替代
- **先 push commit，再 push tag** — 分开两次 push，确保 main 分支先更新
- **release-notes.md 必须每次更新** — workflow 始终从该文件读取 Release 正文，不更新会导致所有版本显示相同内容
- **版本号同步** — `build.gradle.kts` 和 `AGENTS.md` 两个文件的版本号必须一致
- **versionCode 递增** — Android 要求 versionCode 严格递增，+1 即可
